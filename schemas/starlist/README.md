# AAVSO Starlist Schema

## Schema description for humans
There is a [human-readable description of the schema](https://github.com/AAVSO/public-utils/blob/main/schemas/starlist/aavso_starlist_schema_data/schema_definition.md) available. In brief, a star file contains a single StarListSet, corresponding to one or more images, which contains one or more `StarList`s. Each StarList contains one or more `StarItem`s, which describe the stars in the image, along with metadata about the image and star list.

## Schema description for computers
The JSON schemas that can be used to validate starlists in a number of programming languages are in the [schema definition folder](https://github.com/AAVSO/public-utils/tree/main/schemas/starlist/aavso_starlist_schema_data). Each released version is archived in its own `v<version>/` folder (for example `v0.3.1/schema_definition.json`); the current version is the one in the highest-numbered folder, and a duplicate of it is also at the top of the folder, called [`schema_definition.json`](https://github.com/AAVSO/public-utils/blob/main/schemas/starlist/aavso_starlist_schema_data/schema_definition.json).

## Schema tools for Python

### Installation

The package is not on PyPI; install it from this repository:

```bash
pip install "aavso-starlist-schema @ git+https://github.com/AAVSO/public-utils.git#subdirectory=schemas/starlist"
```

### Usage

#### From Python: Generate the schema

```python
from aavso_starlist_schema import generate_star_list_set_schema, generate_starlist_schema

# Schema for a StarListSet (the file manufacturers submit; this is what the
# reference file under aavso_starlist_schema_data/ and the command-line tool produce)
print(generate_star_list_set_schema())

# Schema for a single StarList
print(generate_starlist_schema())

# Save the schema to a file
with open("starlist_schema.json", "w") as f:
    f.write(generate_star_list_set_schema())
```

#### From python: Generate a markdown table describing the schema

```python
from aavso_starlist_schema import StarList, StarListSet

print(StarListSet.markdown_table())
print(StarList.markdown_table())
```

#### From python: Check that a starlist file is valid

```python
from aavso_starlist_schema import validate_file

# Validate the file and upgrade it to the current schema version if it is
# older (with a SchemaMigrationWarning); returns a StarListSet
star_list_set = validate_file("starlists.json")

# Validate the file against the schema of its own generation, without
# upgrading it; returns that generation's model, no warning (a file from an
# older release of the current generation is read as the current version).
# Only that generation's limits apply; see "Reading starlist files".
as_written = validate_file("starlists.json", as_written=True)
```

An invalid file raises the pydantic `ValidationError`, which names the field;
see [Reading starlist files](#reading-starlist-files) for the version errors.

#### From the command line

A console script is installed with the package:

```bash
# Validate a starlist file: prints "<file>: valid (schema version <version>)",
# plus a line describing the upgrade if the file is from an older version, and
# exits with status 0; for an invalid file prints the reason to stderr and
# exits with status 1
aavso-starlist-schema validate <file>

# Validate against the schema version the file states, without upgrading it;
# a file from an older release of the current generation is read as the
# current version; only the limits of its generation apply, so an older file
# may pass that the current schema would refuse
aavso-starlist-schema validate <file> --as-written

# Write the JSON schema to <path> with its suffix replaced by .json
aavso-starlist-schema write-schema <path>

# Write a markdown table to <path> with its suffix replaced by .md
aavso-starlist-schema write-schema <path> --markdown
```

`validate` only reads its file, which is used exactly as given (no suffix is
added). `write-schema` refuses to overwrite a file that already exists unless
`--force` is given, so neither command can damage a starlist file by mistake.
Run `aavso-starlist-schema --help` for the details.

### Reference schema files

The reference schema files under `aavso_starlist_schema_data/` are **autogenerated** and should not be
edited by hand. Regenerate them after changing the schema:

```bash
uv run poe generate
```

The pre-commit hook described under Development does this automatically.

### Schema versioning

The schema has its own hand-maintained semantic version, `SCHEMA_VERSION` in
`aavso_starlist_schema.py`. It is deliberately **independent of the package
version** (which comes from git tags): the schema version identifies the
contract that starlist files are written against, so it only changes when the
schema itself changes.

`schema_version` is a required field of a starlist file (`StarListSet`). There
is no default: code that builds a `StarListSet` passes
`schema_version=SCHEMA_VERSION` explicitly (data without one is treated as a
legacy file and upgraded with a warning, see below). The generated
`schema_definition.json` also states its own version in a top-level
`version` key.

#### Version policy

| Change | From 1.0.0 on | While 0.y.z |
| --- | --- | --- |
| Description, a unit written another way with the same meaning, or other annotation only | patch | patch |
| New optional field | minor | patch |
| New required field, removal, changed meaning | major | minor |

A *generation* is a set of versions that need no migration between them: a
reader reads any released version of its own generation up to its own version,
and refuses newer ones. The generations are `0.2` for 0.2.z, `0.3` for 0.3.z,
`0.4` for 0.4.z (the current one), and so on, then `1` for 1.y.z, and
`legacy` for everything before 0.2.0 (files with no `schema_version`,
package-version strings such as `0.0.1.dev451+gde1568f`, or a version below
0.2.0 such as `0.0.1`).
Crossing a generation boundary requires a migration.

From 0.4.0 the models forbid keys they do not define (`additionalProperties:
false` in the schema), reject infinity and NaN in every float field,
require `stack` to be 1 or more or `null`, and cap the length of each string
field and the number of star items (see `schema_definition.json` for the
limits).

Every generation that has been left behind keeps a *frozen* copy of its models
in its own module (`_aavso_starlist_legacy.py` for the legacy generation,
`_aavso_starlist_v0_2.py` for 0.2, `_aavso_starlist_v0_3.py` for 0.3), so
that an old file can still be validated against the schema it was written for.
The live models in `aavso_starlist_schema.py` are always the current generation.

Every schema version is archived unchanged in a `v<version>/` folder under
`aavso_starlist_schema_data/` (for example `v0.2.0/`). The
`schema_definition.*` files directly under it are always the current schema; the archive is the record of what each version looked like. The tests
require the current files to match the archive for `SCHEMA_VERSION`, so a
schema change without a version bump fails `pytest`, and CI rejects a pull
request that modifies or deletes an archived file. The tests also require each
frozen model to generate exactly the newest archived schema of its generation
(`legacy/` for the legacy models), which is what keeps it frozen
(`fail_fast=True` on the list fields, which leaves the schema and the set of
valid files unchanged, is the one exception).

#### Changing the schema

First decide, from the policy above, whether the change starts a new
generation. While the schema is `0.y.z`, every minor bump is a new generation,
but only a breaking change takes one: a new optional field is a patch bump
(0.2.0 → 0.2.1) and stays in the same generation. This is the convention
Cargo uses for `0.y.z` versions, chosen so that a minor bump while `0.y.z`,
like a major bump from 1.0.0 on, always means a migration is needed.

The steps are listed in the order they are done. The ones marked *new
generation only* are for a breaking change (0.2 → 0.3, or 1 → 2 from 1.0.0
on). Any other change (a patch bump while `0.y.z`, a minor or patch bump from
1.0.0 on) skips them: it only changes the models, bumps the version,
generates, archives and runs the tests.

1. *New generation only.* Before touching the live models, make a frozen copy
   of the models of the generation being left, in a new module named for it,
   e.g. `_aavso_starlist_v0_2.py`, made when leaving 0.2. Copy
   `AAVSOFilters`, `StarItem`, `StarList` and `StarListSet` with their fields
   only: no mixins, no methods, no validators that upgrade. Replace anything
   computed from `SCHEMA_VERSION` (the `version` key and the `schema_version`
   examples and pattern) with the literal value. The module must not import
   from `aavso_starlist_schema`. `_aavso_starlist_v0_2.py` is the example to
   follow. Check the copy straight away with
   `uv run pytest -k test_frozen_model_matches_its_archive`: the test finds
   every `_aavso_starlist_*.py` module by its name, registered or not, and
   passes once the copy generates the same schema as the newest archive of its
   generation, which before the version bump is the current schema.
2. Change the live models in `aavso_starlist_schema.py`, bump
   `SCHEMA_VERSION` following the policy above, and add the new version to
   `_RELEASED_VERSIONS` just below it.
3. Run `uv run poe generate` to regenerate the reference schema files.
4. Run `uv run poe archive` to copy them to their `v<SCHEMA_VERSION>/` archive.
5. *New generation only.* Write a migration function from the old generation
   to the new one, and register it in `_MIGRATIONS` in
   `aavso_starlist_schema.py` together with the frozen `StarListSet`.
   `_migrate_legacy_to_0_2` is the template for a no-op migration, when no
   data has to change, and `_migrate_0_2_to_0_3` for one that fills in a new
   required field. `_migrate_0_3_to_0_4` is the template for one that drops
   what the new generation forbids and raises `ValueError`, naming the field,
   for a file it cannot repair. A migration is never edited once released. It
   takes a dict and returns the migrated dict; `upgrade()` stamps the target
   version on the result. It is given a deep copy, so it may modify its
   argument in place. Through `model_validate_json`, `model_validate` and the
   constructor, the dict holds only plain JSON data (dicts, lists, strings,
   numbers, booleans and `None`): data built in Python is converted once the
   frozen model has accepted it. The first migration receives only the keys
   that the frozen model of the file's own generation defines, so every value
   it sees was validated, and each later one what the migration before it
   produced. `upgrade()` called directly validates and converts nothing. The
   `_Migration` docstring has the details.
6. *New generation only.* Add a `before.json`/`after.json` pair of sample
   files under
   `tests/data/migrations/<old generation>_to_<new generation>/`, e.g.
   `legacy_to_0.2`, `0.2_to_0.3`, `0.9_to_1`. `before.json` must be valid for
   the frozen model of the old generation and `after.json` for the new one.
7. Run `uv run pytest`. It treats an unexpected `SchemaMigrationWarning` as an
   error, so a test that reads a file of an older generation must expect the
   warning with `pytest.warns(SchemaMigrationWarning)`; after a breaking bump
   that includes any test written when that generation was current.

A breaking bump without its migration fails many tests, not one. With no
migration out of the generation being left, files of every older generation
have no path to the current one either, so each test that upgrades a legacy
file fails too. Most report `DID NOT WARN`, because the upgrade stops before
it warns; the traceback below shows the `UnsupportedSchemaVersionError` that
names the generation with no migration and calls it a gap in the migration
chain. Look first at
`test_migration_chain_reaches_current_generation`, which names the missing
migration. A migration without its sample files fails
`test_each_migration_step_matches_its_before_after_pair`.

#### Reading starlist files

Use the standard pydantic methods. `StarListSet.model_validate_json(text)`,
`StarListSet.model_validate(data)` and the constructor all read older data. A
file from an older generation goes through three steps:

1. It is validated against the frozen model of its own generation: is this
   file valid for the schema version it states? Keys that frozen model does
   not define are dropped first, at every level, without their values being
   read: the frozen model ignores them, and nothing downstream may use a
   value no schema validated, even under a key a later generation defines.
   One-shot iterators such as generators and list-like containers (deques,
   arrays and the like) under list fields are first read, once, into lists;
   under a list of plain values such as `photometry_software` only that one
   level is read, and its items are validated as given. A model instance of
   the file's own generation is read as its fields and validated like a
   dict. Everything else is validated as given.
2. It is converted to plain JSON data (lists are copied, other mappings
   become dicts, model instances dicts of their fields, enum members their
   values; any other value is kept a scalar, even one that is iterable)
   and upgraded to the current schema version with `upgrade()`, as a plain
   dict, one generation at a time. Nothing is validated between migrations.
3. The result is validated against the current model.

A file already in the current generation only gets step 3.

```python
from pathlib import Path

from aavso_starlist_schema import StarListSet

star_list_set = StarListSet.model_validate_json(Path("starlists.json").read_text())
```

`validate_file(path)` is the file-level convenience: it reads and parses the
file and validates it the same way, or, with `as_written=True`, as
`validate_as_written` below does.

The first two steps are also available on their own:

- `validate_as_written(data)` takes the parsed dict and validates it against
  the schema of its own generation, without migrating it to a newer
  generation. It returns the validated model: a `StarListSet` for a current
  file (which states the current version), the frozen model for an older one.
- `upgrade(data)` takes the parsed dict and returns a dict in the current
  generation, stamped with the current version. The result is always a copy; the
  input is not modified. It does not validate, and it passes the values
  inside to the migrations as given, without converting them to plain data.

`validate_as_written` answers only whether a file is valid for the generation
of the version it claims. It does not apply anything a later version added: a 0.3.x file may
hold infinity or NaN, strings of any length, more than 100000 star items or a
`stack` of 0, and `model_dump(mode="json")` of the result emits them as they
are. To hold every file to the current schema, read it with
`StarListSet.model_validate` or `validate_file(path)`, which upgrade it.

A file from an older version of the current generation needs no migration; it
is read without a warning, and the object states the current version.

Version handling applies to mappings and JSON input, not to `from_attributes`
validation.

A file from any newer version, even one in the same generation, is refused
with `NewerSchemaVersionError`: this version cannot know what changed, and a
newer version in the same generation (a patch while `0.y.z`, a minor from
1.0.0 on) may add fields it would silently drop. The `schema_version` pattern in the generated schema lists exactly
the versions that are read without upgrading.

When a file is upgraded, a `SchemaMigrationWarning` is issued naming the
original version, the new version and what changed. The upgraded object is
derived data; the submitted file remains the record.

A file that is not valid for the schema version it states fails step 1 with the
usual pydantic `ValidationError`; that is a problem with the file. Validation
stops at the first bad entry of a list field, so an invalid file reports its
first bad star item, star list or software entry rather than all of them. A
file a migration refuses in step 2, because the new generation cannot hold
it, raises the same `ValidationError`. The 0.3 to 0.4 migration drops keys
the 0.3 schema did not define (the 0.3 reader ignored them) and turns a
`stack` of 0 or less into `null`, but a float that is infinite or NaN, a
string longer than 0.4.0 allows, or a star list of more than 100000 star
items has no 0.4 form:
the migration raises `ValueError` naming the field, and `upgrade()` called
directly raises that `ValueError` itself. The field is named in the error
message, not in pydantic's `loc` (which is empty), and only the first such
problem is reported. Either way it is not a `MigrationResultError`, since the
package is not at fault.

Three errors are specific to versioning. All derive from `SchemaVersionError`,
which is deliberately not a `ValueError`, so pydantic does not wrap them in a
`ValidationError`:

- `NewerSchemaVersionError`: the file was written against a newer schema than
  this version of the package understands. Upgrade the package.
- `UnsupportedSchemaVersionError`: the version cannot be understood, was never
  released (it is 0.2.0 or later, not newer than this package's version, and
  has no `v<version>/` archive), or there is no migration path from
  it.
- `MigrationResultError`: the file was valid for its own version (step 1) but
  the upgraded data was not valid (step 3). That is a bug in a migration in
  this package, not a problem with the file.

## Development

This project uses [uv](https://docs.astral.sh/uv/) and is versioned from git
tags via `hatch-vcs`. Project tasks are defined with
[poethepoet](https://poethepoet.natn.io/) in `pyproject.toml`. Run these
commands from `schemas/starlist`:

```bash
uv sync --extra dev      # create the environment and lockfile
uv run pytest            # run the tests
uv run poe               # list the available tasks
uv run poe generate      # regenerate the reference schema files
uv run pre-commit install # install the git pre-commit hook (once per clone)
```

The repo-level `.pre-commit-config.yaml` runs `poe generate` whenever the schema
module or the reference files are part of a commit. If that changes a file the
commit is rejected; `git add` the regenerated files and commit again. The hook
needs `uv` on your `PATH`.
